## Findings

### 1. Four-workspace P&L/firm catalog: definite test clock defect

Evidence: `/tmp/icarus-publish-full-final.log:66–78` fails at `clock.pauseAt` with `Cannot fast-forward to the past`. Test `tests_engine/test_command_center_routes.py:464–468` installs a running clock at the fixture P&L timestamp, runs **92 seconds**, awaits an expiry predicate and a locator read, then pauses at the absolute fixture timestamp **+93 seconds**. There is only a one-second budget for everything after `runFor`, plus clock progress during the earlier operations. On a slower host that absolute target has already passed. The log identifies this harness operation, not a product assertion, as the failure. P&L expiry assertions immediately preceding it succeeded.

Narrow fix: pause the installed clock immediately at a comfortably future point (while retaining the valid P&L phase), then advance the paused clock by the intended 92 seconds using `runFor`. Remove the later absolute `pauseAt(+93)` entirely. Alternatively freeze before the expiry scenario and advance relative to its frozen origin. Do not change P&L freshness thresholds. App expiry is independently implemented by `icarus_engine/workspace-dashboard.js:198` (one-second accounting watchdog); live refresh is `:310` (15 seconds).

### 2. Late failed refresh: definite nondeterministic fixture concurrency

Evidence: `/tmp/icarus-publish-full-final.log:79–83` records **two** intercepted selected-status GETs at `tests_engine/test_workspace_dashboard_browser.py:271`, where the test assumes exactly one. The test uses `common_page(workspace_http)` at `:263`, whose `pause_periodic` default is false (`:49`). It installs the hold after awaiting one manual refresh (`:264–266`), starts another manual `refresh()` (`:267`), then counts requests. Real `pollStatus` runs every three seconds (`icarus_engine/dashboard.html:1677`). Its busy guard (`:1491–1496`) only prevents scheduled polls when another refresh is already active; `refresh()` itself admits explicit overlapping requests (`:1477–1482`). Therefore a scheduled poll admitted before the explicit call can overlap it and both hit the new hold. There is no guarantee that a one-time `await refresh()` leaves the future timer phase controlled. The assertion fails before testing stale-failure protection.

Narrow fix: use existing `common_page(workspace_http, pause_periodic=True)` for this manual out-of-order response test. That fixture already clears intervals and waits for both `statusRefreshes` and `statusPollBusy` to drain (`:65–81`). Keep real polling coverage in the separate automatic-flow tests. Retain the late 503 and selected observation assertions. Use a bounded request-arrival predicate and ensure held routes are settled in cleanup. Do not add a global mutex to `refresh()` merely to satisfy this test: newer manual observations must be able to supersede old requests. Existing request-sequence guards are at `dashboard.html:1479–1488` and `workspace-client.js:74–75,103–105`.

### 3. Automatic status during chart deadline: unresolved freshness failure, not established as test-only

Evidence: `/tmp/icarus-publish-full-final.log:141–147` records `{lost: False, count: 35, age: 9720}` at `tests_engine/test_workspace_dashboard_browser.py:874`. Status remained present and the synthetic catalog retained all 35 assets, but the last accepted status was 9.72 seconds old. This violates the test's four-second bound and lies just below the app's **10-second** observation watchdog (`dashboard.html:1476`). The log gives no intercepted status count because `assert len(statuses)>=3` occurs **after** the failing freshness assertion (`test:875`). It supplies neither request timings nor busy-state snapshots. It therefore cannot prove that periodic status remained healthy, or that the app has a chart/status coupling race.

Source separates the flows: `pollStatus()` awaits only `refresh()` (`dashboard.html:1491–1496`); the chart pass has its own single-flight promise and four Main workers (`:1587–1612`); chart errors clear only that chart (`:463–466`). There is no direct await of chart work in the periodic status loop. The client enforces a real 10-second deadline independently per request (`workspace-client.js:38,64–82,103–111`). These facts rule out a simple explicit await dependency, not event-loop starvation, transport contention, or delayed interception.

The test also has an uncontrolled setup interval: it waits for idle **before** `_full_main`, captures two values, and only then installs status/chart routes (`test:848–863`). `_full_main` renders a synthetic catalog without refreshing `lastStatusAt` (`:649–658`); real timers remain active throughout. Thus a status request can begin before mock interception, and setup can consume freshness budget. A wall-clock snapshot immediately after the deadline predicate is sensitive to slow host/render scheduling. These are credible fixture races; the available log does not identify which happened.

Narrow fix/next diagnostic: install permanent status interception before synthetic setup and explicitly observe an accepted scheduled status baseline before starting the held NQ request. Record each status request/fulfillment/acceptance time, `statusRefreshes`, `statusPollBusy`, `statusLoadSeq`, chart start/deadline times, and maximum accepted-status gap **during** the chart hold. Use controlled browser clock advancement in small steps with route pumping, or an event-based bounded progression check for real timer coverage. Preserve the production 10-second deadline/watchdog and the requirement that status progresses while the chart remains pending. Do not classify this green by raising the four-second bound to 10+ seconds or removing the assertion. A real accepted-status gap approaching 10 seconds remains a product freshness defect to investigate after fixture isolation.
