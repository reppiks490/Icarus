# A200 catalog implementation and current readiness

Date: 2026-10-16
Branch: `main` (PR #368)
Contract: `2026-10-15-market-universe-200-contract.md`

## Catalog delivered

The checked-in catalog contains 200 distinct US-listed common stock, ordinary share, and depositary receipt listings from Nasdaq, NYSE, and NYSE American's public stock screener. The builder requests market-cap ordering, selects from the screener-reported values, discards those values, and records response hashes plus source retrieval metadata. This is a hash-anchored snapshot, not an independently reproducible ranking: raw source responses and market-cap values are not retained. The anomalous SPCX record is explicitly quarantined and unsupported security classes such as preferred shares, warrants, and units are excluded.

Each row has a provisional exchange-plus-symbol listing identity, candidate Yahoo and FMP symbol mappings, an explicit instrument type, and unknown fields where the source snapshot does not establish tick size, share/point value, corporate-action treatment, terms, entitlements, or historical/live bar quality. Yahoo symbol echoes have been observed, but the provider mappings are still unverified as canonical listing crosswalks. All 200 are `pulse_enabled=false` and `strategy_qualified=false`.

## Connection state

The engine exposes the catalog at `GET /api/market-universe` and in the Market Data dashboard. The API reports 200 catalogued and zero source-connected, historical-qualified, live-qualified, Pulse-enabled, or strategy-qualified entries. It has no feed or broker side effects and does not change the existing runtime asset registry.

`MarketUniverseAdapter` now resolves the catalog-declared Yahoo candidate mapping by provisional instrument ID and can fetch a requested historical batch. It rejects unknown IDs, unsupported intervals, and provider-symbol mismatches, and returns a checksum receipt. An echoed ticker records `provider_symbol_match_status=MATCHED`; because the listing crosswalk is still unverified, canonical `identity_status` remains `PROVISIONAL`. The adapter does not activate Pulse or update catalog counts; Yahoo entitlement and market-session qualification remain unknown.

A read-only probe sweep requested one daily historical window for all 200 candidates on 2026-10-15. Yahoo returned bars and echoed the requested symbol for all 200 rows. The packaged probe ledger at `icarus_engine/a200-yahoo-history-probe.json` contains response counts, time bounds, checksums, and receipts only; raw OHLCV is not stored. It reports 200 provider responses and 200 symbol matches, but zero canonical identities verified, entitlements verified, or historical batches qualified. The UI exposes those probe observations separately from the source-connected and qualification counts and marks results stale after 24 hours.

The provider-separated hybrid report at `icarus_engine/a200-hybrid-history-probe.json` records a fresh 2026-10-16 historical probe for each catalog/provider pair. Yahoo returned bars and matching symbol echoes for 200/200 candidates; FMP was `NOT_CONFIGURED` for 200/200 because no `FMP_API_KEY` was available to the probe process. The ledger stores receipt metadata, counts, and checksums, never raw OHLCV. Its loader binds every pair to the catalog snapshot, verifies the result digest and per-result timestamps, and marks the report stale after 24 hours. The API and dashboard show Yahoo and FMP states independently. This is evidence of Yahoo response availability only: canonical identity and entitlements remain unverified, qualification remains 0/200, and Pulse remains disabled.

The listing identity crosswalk at `icarus_engine/a200-listing-crosswalk.json` compares the 200 catalog venue/symbol/name/instrument-type/depositary-ratio tuples with the Nasdaq-operated public stock screener. It stores source response SHA-256 digests and retrieval times, the catalog digest, and per-listing identity hashes; it does not persist market capitalization or quote fields. The loader rejects catalog drift, missing/duplicate rows, invalid hashes, stale reports, and mismatched `MATCHED` rows. Since the raw source responses are deliberately not persisted, the loader can validate the source digest format but cannot independently recompute those digests from the extracted listing rows; rerun the builder to fetch fresh source responses. The Market Data dashboard reports these matches under a distinct public-listing identity count. The crosswalk verifies only that public exchange metadata matches the catalog snapshot. It does not prove provider symbol mapping, account entitlement, usable history/live data, runtime connection, Pulse or strategy qualification, or execution authority. These remain separate and unchanged at zero.

To probe one representative instrument with the safer Yahoo-only default, run `PYTHONPATH=. python tools/probe_a200_hybrid.py --limit 1`; the default output is `reports/a200-hybrid-history-probe.json`, so a small diagnostic run cannot replace the packaged API ledger. FMP is not initialized or contacted unless explicitly selected with `--providers fmp`; to request both providers, pass `--providers yahoo fmp`. A full 200-instrument provider sweep can make many external requests, so select only providers with established endpoint entitlement and an appropriate request budget. To refresh all 200 and publish its validated status through the API, run `PYTHONPATH=. python tools/probe_a200_hybrid.py --limit 200 --providers yahoo --out icarus_engine/a200-hybrid-history-probe.json`. Each report binds its requested UTC window and uses a 0.25-second inter-instrument pause. Do not interpret a configured provider or a successful response as entitlement, canonical mapping, qualification, or execution authority.

Existing registered-asset historical warm-up now records a bounded per-run receipt history with provider, expected/observed symbol, interval, window, timestamps, row count, checksum, alignment, and observed gap count. A receipt can count as qualified only when the caller supplies the complete expected bar-start schedule generated from the authoritative exchange calendar for the requested session window. That schedule detects missing bars at both window edges as well as between returned rows. Receipt IDs include the validation evidence, so identical bars with different identity, entitlement, or coverage states cannot collide. Receipt identity or entitlement uncertainty remains visible; session qualification is unknown and therefore no batch is counted as A200-qualified. These receipts do not establish connectivity for the 200 catalog candidates.

This is not a claim that 200 assets are fully connected. Connection requires confirmed provider mappings and account entitlements, receipt-validated bars, execution-critical metadata, and the acceptance gates in the A200 contract. Those steps remain pending the source and entitlement evidence.
